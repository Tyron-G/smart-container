# smart-container 核心业务链路说明

> 更新时间：2026-05-30

## 1. 文档目的

本文档用于从业务流程角度，串联 `smart-container` 项目中最核心的几条链路，帮助理解各微服务之间如何协作，以及“管理端 / 用户端 / 设备端”是如何共同完成完整业务闭环的。

本文档重点关注以下四条链路：

1. 用户扫码开柜链路
2. 支付/签约回调链路
3. 设备心跳与事件上报链路
4. 管理端配置生效链路

> 说明：本文档基于当前仓库可见代码、模块职责和接口语义进行整理，属于“系统理解文档”，并不等价于完整产品需求文档。

---

## 2. 总体业务模型

从当前项目代码来看，系统面向的是一个**智能货柜 / 无人零售柜**场景。

参与的核心角色包括：

- **用户端**：消费者扫码、授权、支付、开柜购物
- **管理端**：运营人员配置优惠券、业务规则与管理参数
- **设备端**：货柜硬件上报心跳、接收开门命令、上报设备事件
- **后端微服务**：完成订单、支付、设备、通信、配置等业务编排

可简化为以下结构：

```text
用户端  -> order / channel / account
管理端  -> manager
设备端  -> communicate / device
公共层  -> api / common
```

## 3. 用户扫码开柜链路

这是当前系统最核心的一条业务链路。

### 3.1 链路目标

目标是完成一次从“用户扫码”到“设备开门”再到“订单建立”的闭环。

### 3.2 涉及模块

- `container-order`
- `container-channel`
- `container-device`
- `container-communicate`
- `container-account`（间接）

### 3.3 典型参与接口/文件

#### order 模块
- `container-order/src/main/java/cn/fuguang/order/controller/OrderController.java`
- `container-order/src/main/java/cn/fuguang/order/controller/CustomerController.java`
- `container-order/src/main/java/cn/fuguang/order/controller/SmsController.java`

#### device 模块
- `container-device/src/main/java/cn/fuguang/device/feign/DeviceOperateFeignServiceImpl.java`
- `container-device/src/main/java/cn/fuguang/device/feign/DeviceInfoFeignServiceImpl.java`

#### communicate 模块
- `container-communicate/src/main/java/cn/fuguang/communicate/protocol/netty/server/NettyServer.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/command/impl/yinuo/YNOpenGateCommand.java`

### 3.4 业务步骤（推断链路）

#### 第一步：用户扫码进入业务流程
用户在货柜上扫码后，前端或移动端会进入订单/用户确认流程。

可能入口包括：
- `/order/order/scanResultWithConfirm`
- `/order/customer/scanResultWithConfirm`

这一步的作用通常是：
- 识别货柜/设备
- 识别当前用户
- 判断是否允许继续购物流程

#### 第二步：用户完成身份绑定或校验
若用户还未绑定身份，系统可能触发：
- 手机验证码发送
- 支付宝身份绑定

典型接口：
- `/order/customer/sendValidateSms`
- `/order/customer/bindingAliCustomer`

这一步的目标是：
- 建立用户身份与平台账号关系
- 保证后续订单、支付与风控可追踪

#### 第三步：订单服务创建或准备订单上下文
`order` 模块会基于设备、用户、扫描结果等信息准备订单上下文。

从代码结构看，相关业务可能涉及：
- `OrderBizImpl`
- `CustomerBizImpl`
- `OrderServiceImpl`
- `VerifyCodeServiceImpl`

这一步的目标通常包括：
- 生成订单号
- 校验用户是否已有未完成订单
- 校验设备状态是否允许开门
- 记录当前开门申请

#### 第四步：order 调 device，请求开门
订单服务不会直接跟硬件协议打交道，而是通过 `device` 侧能力发起开门动作。

典型内部接口：
- `/device/device/createOrderOpenGate`

这说明：
- `order` 负责业务侧决策
- `device` 负责设备业务动作抽象

#### 第五步：device / communicate 向设备下发开门命令
`device` 不一定直接 TCP 发命令，而是经由 `communicate` 服务完成协议层动作。

`communicate` 中存在典型命令实现：
- `YNOpenGateCommand`

说明真实链路更像：

```text
用户端 -> order -> device -> communicate -> 设备
```

#### 第六步：设备开门并持续上报状态
设备开门后，会继续通过通信层上报：
- 心跳
- 开门结果
- 设备事件
- 可能还有重量/状态变化

此时系统开始进入“购物中 / 设备监控中”的状态。

### 3.5 这条链路的关键特点

1. **订单与设备解耦**
   - `order` 负责业务流程
   - `device` / `communicate` 负责设备动作与协议

2. **用户身份是前置条件**
   - 支付宝绑定 / 短信验证这类流程说明用户身份是开柜前的重要一环

3. **服务间协作明显**
   - 这不是单服务闭环，而是多微服务协同完成

## 4. 支付/签约回调链路

这条链路主要描述用户与第三方支付平台交互后的结果，是如何回流到订单系统中的。

### 4.1 链路目标

目标是处理：
- 支付授权
- 预授权签约
- 第三方支付/签约结果回调
- 回调后订单或用户状态变更

### 4.2 涉及模块

- `container-channel`
- `container-order`
- `container-account`（可能间接参与）

### 4.3 典型参与接口/文件

#### channel 模块
- `container-channel/src/main/java/cn/fuguang/channel/controller/AliPayController.java`
- `container-channel/src/main/java/cn/fuguang/channel/fegin/AlipayFeignServiceImpl.java`
- `container-channel/src/main/java/cn/fuguang/channel/config/AlipayChannelConfig.java`

#### order 模块
- `container-order/src/main/java/cn/fuguang/order/feign/OrderFeignServiceImpl.java`
- `container-api/src/main/java/cn/fuguang/api/order/OrderFeignService.java`

### 4.4 业务步骤（推断链路）

#### 第一步：用户发起授权/签约/支付
这一阶段通常由用户端触发，通道服务 `channel` 负责调用支付宝、微信等第三方平台。

典型能力包括：
- agreementSign
- oauthToken
- sendSms

说明 `channel` 本质上是：
- 第三方支付/授权接入层

#### 第二步：第三方平台回调 channel
支付或签约处理完成后，支付宝等平台不会回调用户前端，而是直接回调后端：

典型入口：
- `/channel/alipay/agreementSignCallBack`

这说明：
- `channel` 是接收外部支付回调的第一站

#### 第三步：channel 把结果回传给 order
回调落到 `channel` 后，`channel` 不会独自完成业务状态更新，而是把结果传给 `order`：

内部接口：
- `/order/agreementSignCallBack`

这条内部链路对应：
- `OrderFeignService`
- `OrderFeignServiceImpl`

#### 第四步：order 更新订单/签约/用户状态
订单服务收到回调结果后，会处理：
- 订单状态变更
- 签约状态落库
- 用户与订单关系更新

可能还会联动：
- 客户签约表
- 客户状态表
- 支付状态字段

### 4.5 这条链路的关键特点

1. **第三方回调不直接打订单服务**
   - 而是先进 `channel`
   - 再由 `channel` 通知 `order`

2. **支付通道和订单域分层明确**
   - `channel` 负责外部平台对接
   - `order` 负责内部订单状态落地

3. **这是一条典型“外部平台 -> 通道层 -> 业务层”的链路**

## 5. 设备心跳与事件上报链路

这条链路体现的是货柜设备如何持续与后台保持连接，并上报运行状态。

### 5.1 链路目标

目标是完成：
- 设备上线与连接保持
- 心跳上报
- 设备事件上传
- 设备状态同步到业务层

### 5.2 涉及模块

- `container-communicate`
- `container-device`
- `container-common-rocketmq`
- `container-common-redis`

### 5.3 典型参与文件

#### communicate 模块
- `container-communicate/src/main/java/cn/fuguang/communicate/command/impl/yinuo/YNHeartCommand.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/command/impl/yinuo/YNOpenGateCommand.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/protocol/netty/server/NettyServer.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/feign/EventAcceptFeignServiceImpl.java`

#### device 模块
- `container-device/src/main/java/cn/fuguang/device/listener/mq/CommunicateEventListener.java`
- `container-device/src/main/java/cn/fuguang/device/biz/impl/CommunicateEventBizImpl.java`
- `container-device/src/main/java/cn/fuguang/device/listener/redis/RedisKeyExpireListener.java`

### 5.4 业务步骤（推断链路）

#### 第一步：设备与 communicate 建立 TCP/Netty 连接
`communicate` 启动时会拉起 Netty server，监听设备接入。

设备不是通过浏览器访问，而是通过协议连接接入。

#### 第二步：设备定时发送心跳
设备会周期性上报心跳。

典型命令：
- `YNHeartCommand`

这一步的作用是：
- 证明设备在线
- 维持设备状态可见
- 为设备状态巡检提供数据

#### 第三步：通信层解析设备消息
`communicate` 服务负责：
- 协议解析
- 根据设备厂商/协议路由命令处理器
- 将设备消息转为业务事件

#### 第四步：事件流转到 device 业务层
通信事件会通过内部 HTTP 或 RocketMQ 进入 `device` 模块：
- `eventAccept`
- `CommunicateEventListener`

这一步说明 `communicate` 和 `device` 的职责是分层的：
- `communicate` 负责“听懂设备协议”
- `device` 负责“理解设备业务含义”

#### 第五步：device 更新设备状态与业务信息
`device` 收到心跳/事件后，可能做：
- 更新设备在线状态
- 记录心跳时间
- 触发业务处理
- 按需通过 Redis / MQ 做延时或异步逻辑

#### 第六步：Redis 过期事件辅助判断设备异常
从代码结构看，系统曾使用 Redis key 过期机制辅助设备心跳异常判断：
- `RedisKeyExpireListener`
- `HeartCountExpireProcessor`

也就是：
- 如果规定时间内没有新的心跳刷新 key
- key 过期后就触发业务逻辑
- 从而判断设备异常或离线

### 5.5 这条链路的关键特点

1. **设备协议层和设备业务层分离**
   - `communicate` 做通信协议
   - `device` 做设备业务

2. **心跳不是单纯日志，而是业务判断依据**
   - 心跳会进入状态判断、过期判断、事件处理逻辑

3. **MQ / Redis 是设备链路的重要支撑**
   - RocketMQ 用于事件异步流转
   - Redis 用于状态缓存与超时判断

## 6. 管理端配置生效链路

这条链路描述的是：后台配置如何影响实际业务运行。

### 6.1 链路目标

目标是说明：
- 管理员在后台配置业务参数
- 配置如何进入后端服务
- 配置最终如何影响用户侧业务结果

### 6.2 涉及模块

- `container-manager`
- `container-order`
- `container-device`
- `container-channel`
- Nacos 配置中心（环境层面）

### 6.3 典型参与文件

#### manager 模块
- `container-manager/src/main/java/cn/fuguang/manager/controller/CouponController.java`
- `container-manager/src/main/java/cn/fuguang/manager/service/impl/CouponServiceImpl.java`
- `container-manager/src/main/resources/mapper/CouponMapper.xml`

### 6.4 业务步骤（推断链路）

#### 第一步：管理员通过后台发起配置操作
例如：
- 新增优惠券配置
- 调整运营参数
- 维护设备或业务规则

典型接口：
- `/manager/api/manager/coupon/addCouponConfig`

#### 第二步：manager 写入业务配置数据
配置不会停留在前端，而会写入数据库或统一配置源。

例如优惠券配置大概率会进入：
- 优惠券配置表
- 业务参数表

#### 第三步：其他服务在业务执行时读取这些配置
例如：
- 订单服务在创建订单时读取可用优惠信息
- 支付链路在结算时计算优惠额度
- 设备业务可能根据运营策略决定是否允许某些动作

#### 第四步：配置通过业务结果体现给终端用户
最终效果可能表现为：
- 用户看到不同的优惠结果
- 某些设备行为受运营规则影响
- 订单金额、支付流程、活动资格发生变化

### 6.5 这条链路的关键特点

1. **管理端并不直接服务用户，而是通过“配置影响业务”**
2. **manager 是典型后台运营配置入口**
3. **真正生效点分散在 order / channel / device 等业务模块中**

## 7. 四条核心链路之间的关系

这四条链路并不是彼此独立的，而是相互交织：

### 用户扫码开柜链路
决定：
- 如何发起一次购物流程

### 支付/签约回调链路
决定：
- 用户是否完成授权/支付状态闭环

### 设备心跳与事件上报链路
决定：
- 设备是否在线、是否正常响应、是否能真正执行开门

### 管理端配置生效链路
决定：
- 运营规则、优惠策略、业务配置如何作用于实际订单和用户体验

可以把它们理解成：

```text
管理端配置 -> 影响业务规则
用户扫码 -> 触发订单流程
订单流程 -> 触发设备动作
设备事件 -> 回流设备与订单状态
支付回调 -> 补全订单闭环
```

---

## 8. 系统核心闭环总结

如果用一句话概括这个系统的核心闭环，可以理解为：

> **用户通过移动端扫码发起购物，后端订单与支付服务完成业务编排，设备通信与设备业务服务完成货柜动作执行，管理端则通过配置持续影响整个业务规则。**

这也是为什么这个项目不能简单理解为“一个后台 + 一个 App”的原因：

它实际上是一个：

## **管理端 + 用户端 + 设备端 + 微服务协作层**

共同完成的智能货柜系统。
