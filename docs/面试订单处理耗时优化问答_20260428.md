# 面试订单处理耗时优化问答

## 1. 平均 3s 缩短至 0.5s 是怎么做的？

这里的 `0.5s` 指的是**下单接口响应时间**，不是从用户下单到设备完整出货完成的总耗时。

原来的下单链路通常是同步串行的：

```text
用户扫码
 -> 查询商品
 -> 查询设备状态
 -> 查询库存
 -> 创建订单
 -> 扣减库存
 -> 调用支付
 -> 下发出货指令
 -> 等设备返回结果
 -> 更新订单状态
 -> 返回用户
```

这个链路慢的原因是：数据库查询多、库存扣减依赖数据库锁、支付和设备通信都在主请求线程里等待，任何一个环节变慢都会拖慢整个下单接口。

优化后把链路拆成同步主链路和异步后置链路：

```text
用户下单
 -> Redis 校验设备状态、商品、库存
 -> Redis Lua 原子扣库存
 -> 创建待支付/待出货订单
 -> 投递 RocketMQ 消息
 -> 立即返回用户
```

后面的支付回调、设备出货、失败退款、库存回滚等流程全部异步处理。

### 核心优化点

1. **商品、库存、设备状态缓存到 Redis**

   原来每次下单都需要查 MySQL，例如：

   ```text
   查设备是否在线
   查货道是否可用
   查商品是否上架
   查库存是否足够
   ```

   优化后这些高频数据提前缓存到 Redis，例如：

   ```text
   device:status:{deviceId}
   device:slot:{deviceId}
   goods:info:{goodsId}
   stock:{deviceId}:{slotNo}
   ```

   下单时大部分校验走 Redis，减少 MySQL 查询和数据库连接压力。

2. **使用 Redis Lua 脚本做库存原子扣减**

   不能简单地 `get stock` 后再 `set stock - 1`，因为高并发下会出现超卖。

   更合理的做法是用 Lua 脚本在 Redis 中一次性完成：

   ```text
   判断库存是否大于 0
   扣减库存
   记录订单库存占用
   返回扣减结果
   ```

   这样既避免数据库行锁竞争，也能保证并发场景下库存扣减的原子性。

3. **把非核心流程异步化**

   用户下单接口只保留必须同步完成的动作：

   ```text
   参数校验
   设备、商品、库存校验
   Redis 库存预扣
   订单落库
   发送 MQ 消息
   返回订单号或支付参数
   ```

   以下动作不再阻塞用户请求：

   ```text
   支付状态确认
   设备出货指令下发
   设备回调处理
   失败补偿
   退款
   通知用户
   日志记录
   统计报表
   ```

   这些流程通过 RocketMQ 消费者异步执行。

4. **订单状态机拆清楚**

   订单不是一次性完成，而是按状态流转：

   ```text
   INIT
    -> WAIT_PAY
    -> PAID
    -> DISPENSING
    -> SUCCESS
   ```

   失败路径示例：

   ```text
   WAIT_PAY -> CANCELLED
   PAID -> DISPENSE_FAILED -> REFUNDING -> REFUNDED
   ```

   这样接口可以快速返回，后续流程靠 MQ、支付回调、设备回调继续推进，并通过状态机保证最终一致性。

5. **数据库层优化**

   常见优化包括：

   ```text
   订单表按 order_no、user_id、device_id 建索引
   库存扣减不再高频打 MySQL
   订单创建只 insert 必要字段
   订单详情、日志、统计异步写入
   避免一次下单查询十几张表
   ```

### 面试回答示例

> 原来的下单链路把库存校验、订单创建、支付调用、设备通信、状态更新都放在同步请求里，平均响应在 3 秒左右。优化时我把链路拆成同步主链路和异步后置链路。同步部分只保留设备状态校验、Redis Lua 原子扣库存、订单创建和 MQ 投递，支付回调、设备出货、失败补偿、退款等流程通过 RocketMQ 异步处理。同时把商品、货道、库存、设备在线状态缓存到 Redis，减少 MySQL 查询和锁竞争。优化后用户下单接口的平均响应时间从 3s 降到约 0.5s，完整出货流程仍由异步状态机保证最终一致性。

需要注意：不要说“整个订单从下单到出货只要 0.5s”。更准确的说法是：**下单接口响应 0.5s，订单完成靠异步流程推进**。

## 2. 平均 3s 缩短至 0.5s 这个时间是通过什么得出来的？

这个时间一般不是凭感觉写的，应该来自**压测结果**或**线上链路监控统计**。

统计口径应该明确为：

```text
下单接口响应时间 = 从用户请求进入后端接口开始
              到后端返回下单结果或支付参数为止
```

也就是统计类似接口：

```text
POST /order/create
POST /order/submit
POST /api/order/create
```

### 常见统计方式

1. **压测工具统计**

   可以用 JMeter、wrk、Apifox、Postman Runner 等工具对下单接口进行压测，分别记录优化前和优化后的平均响应时间。

   示例说法：

   > 我们用 JMeter 对下单接口做压测，模拟用户扫码后提交订单的请求。优化前接口平均响应时间大约 3s，主要耗时在数据库查询、库存扣减和设备通信等待上。优化后将设备通信和后置流程异步化，并用 Redis 缓存和 Lua 扣库存，压测结果显示接口平均响应时间下降到约 0.5s。

2. **接口日志统计**

   在代码里记录接口开始和结束时间：

   ```java
   long start = System.currentTimeMillis();

   try {
       return orderService.createOrder(request);
   } finally {
       log.info("createOrder cost={}ms", System.currentTimeMillis() - start);
   }
   ```

   然后从日志中统计平均耗时：

   ```text
   优化前：createOrder avg cost ≈ 3000ms
   优化后：createOrder avg cost ≈ 500ms
   ```

3. **APM 或监控平台统计**

   如果项目接入 SkyWalking、Arthas、Prometheus、Grafana、Pinpoint 等工具，可以直接查看接口平均响应时间、P95、P99、错误率、吞吐量等指标。

### 面试回答示例

> 这个数据是通过压测和接口日志统计出来的。我们主要统计的是下单接口的响应时间，不是整个出货完成时间。优化前下单接口会同步做库存校验、订单落库、支付处理、设备通信等操作，接口平均耗时大约 3s。优化后把设备通信、支付回调、失败补偿等流程异步化，主链路只保留缓存校验、Redis 原子扣库存、订单创建和 MQ 投递。通过 JMeter 压测和接口耗时日志统计，平均响应时间稳定在 500ms 左右。

只写平均值容易被追问，最好能补充这些指标：

```text
平均响应时间：3s -> 0.5s
P95 响应时间：例如 5s -> 0.8s
QPS：例如 50 -> 200
错误率：接近 0
```

如果没有真实压测数据，简历里建议写得更稳妥：

```text
通过链路异步化、Redis 缓存和库存原子扣减，显著降低下单接口响应时间，核心链路耗时控制在 500ms 左右。
```

## 3. 生产环境怎么进行测试？

生产环境不能直接拿大流量压测，正确方式是**灰度、小流量、可回滚、带监控地验证**。

生产环境主要测两类数据：

```text
1. 真实用户链路耗时
2. 小流量灰度压测结果
```

### 生产测试步骤

1. **先加埋点或接口耗时日志**

   在下单接口入口和出口记录耗时：

   ```java
   long start = System.currentTimeMillis();

   try {
       return orderService.createOrder(request);
   } finally {
       log.info("order_create_cost={}ms, orderNo={}, deviceId={}",
               System.currentTimeMillis() - start,
               orderNo,
               deviceId);
   }
   ```

   然后在线上日志平台中统计：

   ```text
   平均响应时间 avg
   P95 响应时间
   P99 响应时间
   错误率
   超时率
   ```

2. **只对少量设备或少量用户灰度**

   不要一次全量上线，可以按设备、城市、用户比例灰度：

   ```text
   先灰度 1% 用户
   或者只灰度 5 台测试设备
   或者只灰度公司内部账号
   ```

   示例：

   ```text
   deviceId in test_device_list -> 新流程
   其他设备 -> 老流程
   ```

   如果新流程有问题，只影响很小范围。

3. **生产环境用真实设备做小流量验证**

   智能零售项目一定要验证真实设备，因为设备通信、出货回调、网络延迟在测试环境很难完全模拟。

   重点测试场景：

   ```text
   正常下单支付
   设备成功出货
   设备离线下单拦截
   库存不足拦截
   支付成功但出货失败
   出货失败后退款
   MQ 消息重复消费
   MQ 消费失败重试
   ```

4. **生产压测必须控制流量**

   如果确实要在生产环境压测，必须控制范围：

   ```text
   低峰期执行
   限制并发数
   使用测试商品
   使用测试设备
   限制测试账号
   提前通知运维
   准备回滚方案
   ```

   示例：

   ```text
   并发 10 -> 30 -> 50 逐步增加
   每轮观察 5 到 10 分钟
   监控 CPU、内存、数据库连接、Redis、MQ 积压
   ```

5. **看监控，不只看接口时间**

   上线后要同时观察：

   ```text
   下单接口平均耗时
   P95 / P99 耗时
   订单成功率
   支付成功率
   出货成功率
   退款成功率
   RocketMQ 消息堆积
   Redis 命中率
   MySQL 慢 SQL
   设备在线率
   ```

### 面试回答示例

> 生产环境不会直接全量压测。我会先在下单接口加耗时日志和链路追踪，统计 avg、P95、P99。上线时按设备或用户做灰度，比如先放 1% 流量或指定几台测试设备走新流程，其他仍走老流程。然后用真实设备、测试商品和内部账号在低峰期做小流量验证，观察接口耗时、订单成功率、MQ 堆积、Redis 命中率、MySQL 慢 SQL 和设备出货回调。确认平均耗时稳定在 500ms 左右、错误率没有上升后，再逐步扩大灰度比例，最后全量上线。

最关键的一句话：

> 生产环境测的是真实链路表现，但必须通过灰度流量、测试账号、测试设备、监控指标和可回滚方案来做，不能直接对全量生产流量压测。
