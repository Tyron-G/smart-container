# smart-container 系统角色与模块对应说明

> 更新时间：2026-05-30

## 1. 文档目的

本文档用于说明 `smart-container` 项目从业务角色和系统分层视角来看，分别服务于哪些端、各模块承担什么职责，以及模块之间的大致协作关系，帮助后续快速理解系统整体结构。

---

## 2. 总体判断

从当前仓库结构、接口形态、支付/授权能力、设备通信能力来看，这个项目并不是“单纯一个后台系统”，而更像一个典型的**智能货柜 / 无人零售柜后端系统**。

从产品角色上看，至少可以分成三类：

1. **管理端**：给运营、管理员、配置人员使用
2. **用户端**：给消费者使用，可能是 App / 小程序 / H5 / 支付宝 / 微信入口
3. **设备端**：给智能货柜、设备网关、通信协议层使用

此外，还有一层公共基础与服务间通信层：

4. **内部公共层**：接口定义、公共能力、跨服务协作能力

---

## 3. 角色划分

### 3.1 管理端

管理端主要面向：
- 运营人员
- 管理员
- 配置人员
- 商户后台使用者

典型能力包括：
- 优惠券配置
- 设备管理
- 业务配置
- 运营参数维护

其典型特点：
- 路径中常出现 `manager`
- 接口多为配置型、维护型、管理型操作
- 更适合 Web 后台页面调用

### 3.2 用户端

用户端主要面向：
- 消费者
- 扫码使用货柜的终端用户

典型能力包括：
- 扫码
- 登录/授权
- 手机验证码
- 绑定支付宝 / 微信身份
- 创建订单
- 开门购物
- 支付与结算

从当前代码看，用户端未必是纯原生 App，更可能包括：
- App
- 小程序
- H5
- 支付宝侧入口
- 微信侧入口

### 3.3 设备端

设备端主要面向：
- 智能货柜硬件
- 设备通信网关
- 协议适配服务

典型能力包括：
- 心跳上报
- 设备事件接收
- 开门命令下发
- TCP/Netty 协议通信
- 设备状态同步

### 3.4 内部公共层

内部公共层不直接服务某个前端页面或设备，而是：
- 支撑微服务之间的调用
- 统一返回结构
- 提供常量、实体、公共工具
- 定义 Feign 接口
- 支撑 MQ / Redis / 公共基础设施接入

---

## 4. 模块与角色对应关系

| 模块 | 主要服务对象 | 角色判断 | 说明 |
|---|---|---|---|
| `container-manager` | 管理端 | 管理后台服务 | 负责配置、管理、运营类能力 |
| `container-order` | 用户端 | 用户业务核心服务 | 扫码、订单、用户绑定、验证码等 |
| `container-channel` | 用户端 / 第三方平台 / 内部服务 | 通道服务 | 支付、授权、短信、第三方回调 |
| `container-account` | 用户端 + 管理端 + 内部服务 | 公共账户服务 | 用户账户/身份基础能力，偏公共能力 |
| `container-device` | 设备业务层 / 内部服务 | 设备业务服务 | 设备状态、开门动作、设备心跳业务处理 |
| `container-communicate` | 设备端 / 内部服务 | 设备通信服务 | Netty、协议处理、事件接收 |
| `container-api` | 内部服务 | 服务间接口定义层 | 定义 Feign 接口、DTO |
| `container-common` | 内部服务 | 公共基础层 | 公共常量、返回结构、Redis、RocketMQ 等 |

---

## 5. 各模块职责说明

### 5.1 `container-manager`

#### 角色归属
- 主要属于：**管理端**

#### 原因
从接口设计上看，该模块明显是后台管理接口。

典型文件：
- `container-manager/src/main/java/cn/fuguang/manager/controller/CouponController.java`

典型接口：
- `/manager/api/manager/coupon/addCouponConfig`

这类接口具备明显的后台特征：
- 路径中含 `manager`
- 操作是“新增优惠券配置”
- 明显偏配置、运营、管理，而不是普通用户行为

#### 典型职责
- 优惠券配置
- 运营参数管理
- 后台业务维护

---

### 5.2 `container-order`

#### 角色归属
- 主要属于：**用户端**

#### 原因
该模块暴露的能力高度贴近消费者实际使用流程。

典型文件：
- `container-order/src/main/java/cn/fuguang/order/controller/OrderController.java`
- `container-order/src/main/java/cn/fuguang/order/controller/CustomerController.java`
- `container-order/src/main/java/cn/fuguang/order/controller/SmsController.java`

典型能力包括：
- 扫码确认
- 用户绑定
- 手机验证码发送
- 订单创建 / 订单流转

#### 典型职责
- 用户扫码开柜相关订单流程
- 用户身份绑定
- 订单侧业务编排
- 与支付/设备服务协作完成购物流程

#### 补充说明
该模块也包含部分**服务间接口**，例如支付回调后通知订单状态变化，因此不是“只服务用户前端”，但总体仍以用户业务为核心。

---

### 5.3 `container-channel`

#### 角色归属
- 主要属于：**用户端通道服务**
- 同时承担：**第三方平台回调入口** + **服务间通道能力**

#### 原因
该模块集中了支付、授权、短信、回调等能力。

典型文件：
- `container-channel/src/main/java/cn/fuguang/channel/controller/AliPayController.java`
- `container-channel/src/main/java/cn/fuguang/channel/fegin/AlipayFeignServiceImpl.java`
- `container-channel/src/main/java/cn/fuguang/channel/fegin/MWFeignServiceImpl.java`

典型业务特征：
- 支付宝授权
- 微信支付
- OAuth token
- 短信发送
- 预授权签约
- 支付平台回调

#### 典型职责
- 聚合第三方支付/授权能力
- 提供短信、授权、支付相关接口
- 接收第三方回调
- 向订单服务回传支付/签约结果

#### 更准确的理解
这个模块不是普通的“页面后端”，而是：
- 用户端流程中的通道服务
- 第三方生态（支付宝 / 微信）接入层

---

### 5.4 `container-account`

#### 角色归属
- 主要属于：**公共账户服务**
- 间接服务：用户端、管理端、内部服务

#### 原因
当前仓库中可见的 `account` 模块对外 HTTP controller 很少，不像典型业务前台服务；更像一个基础能力模块。

典型文件：
- `container-account/src/main/java/cn/fuguang/account/ContainerAccountApplication.java`

#### 典型职责（推断）
- 账户相关基础能力
- 用户身份/资料基础能力
- 为其他服务提供公共账户支撑

#### 说明
从当前仓库可见代码判断，它不太像一个直接被前端频繁调用的独立模块，而更像：
- 被订单、支付、管理等服务间接依赖

---

### 5.5 `container-device`

#### 角色归属
- 主要属于：**设备业务层**
- 主要面向：内部服务和设备侧业务逻辑

#### 原因
该模块承担的是设备状态与设备动作层面的业务处理，而不是直接设备协议通信。

典型文件：
- `container-device/src/main/java/cn/fuguang/device/controller/DeviceController.java`
- `container-device/src/main/java/cn/fuguang/device/feign/DeviceInfoFeignServiceImpl.java`
- `container-device/src/main/java/cn/fuguang/device/feign/DeviceOperateFeignServiceImpl.java`

典型能力包括：
- 设备状态检查
- 开门操作
- 心跳业务处理
- 设备事件消费
- Redis / RocketMQ 协同处理

#### 典型职责
- 处理设备业务状态
- 接收设备通信层转发过来的事件
- 响应订单服务的设备操作请求

#### 更准确的理解
- 它服务的是“设备业务逻辑”
- 不是直接给设备硬件调用的第一层
- 真正接设备协议的更多是 `communicate`

---

### 5.6 `container-communicate`

#### 角色归属
- 主要属于：**设备端通信层**
- 同时承担：**内部桥接服务**

#### 原因
该模块明显不是普通 HTTP 业务模块，而是设备通信模块。

典型文件：
- `container-communicate/src/main/java/cn/fuguang/communicate/ContainerCommunicateApplication.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/protocol/netty/server/NettyServer.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/command/impl/yinuo/YNHeartCommand.java`
- `container-communicate/src/main/java/cn/fuguang/communicate/command/impl/yinuo/YNOpenGateCommand.java`

典型特征：
- Netty
- TCP 监听
- 心跳命令
- 开门命令
- 协议处理
- 事件接收

#### 典型职责
- 维持设备连接
- 接收设备上报
- 下发设备控制指令
- 对接不同设备协议/厂商

#### 说明
它既有 HTTP 端口，也有额外 Netty 端口，因此不是单纯 Web 服务，而是：
- HTTP + TCP 双栈通信服务

---

### 5.7 `container-api`

#### 角色归属
- 主要属于：**内部服务接口定义层**

#### 原因
该模块集中定义了：
- Feign 接口
- DTO
- 跨服务请求/响应模型

#### 典型职责
- 统一服务间调用契约
- 降低模块间耦合
- 作为微服务接口定义层存在

#### 说明
它不直接服务页面或设备，而是面向开发与微服务内部调用。

---

### 5.8 `container-common`

#### 角色归属
- 主要属于：**公共基础层**

#### 原因
这里集中放了：
- 公共常量
- 通用实体
- 统一返回结构
- Redis 公共配置
- RocketMQ 公共配置
- 工具类

典型内容：
- `container-common/container-common-core`
- `container-common/container-common-redis`
- `container-common/container-common-rocketmq`

#### 典型职责
- 提供所有模块共享的基础设施能力
- 统一返回结构、常量、实体模型
- 支撑 Redis / RocketMQ / 通用工具能力复用

## 6. 系统角色与模块关系图（文字版）

可以把当前系统简化理解成如下结构：

```text
[管理端前端]
      |
      v
container-manager

[用户端(App / 小程序 / H5 / 支付宝 / 微信)]
      |
      +--> container-order
      |
      +--> container-channel
      |
      +--> container-account（部分基础能力）

[设备 / 智能货柜]
      |
      v
container-communicate
      |
      v
container-device

[内部公共层]
container-api
container-common
```

进一步理解为：

```text
管理端  -> manager
用户端  -> order + channel + account(部分)
设备端  -> communicate + device
公共层  -> api + common
```

## 7. 模块协作关系（业务视角）

### 7.1 用户购物链路（典型）

可能的业务流程：

1. 用户扫码货柜
2. 用户通过移动端完成身份识别 / 支付授权
3. `order` 创建订单
4. `order` 调用 `device` 或通过内部链路触发开门
5. `communicate` 向设备下发开门命令
6. 设备上报事件 / 心跳 / 状态
7. `device` / `order` 完成订单与设备状态流转
8. `channel` 处理支付、签约、短信或第三方回调

### 7.2 管理运营链路（典型）

可能的业务流程：

1. 管理员进入后台系统
2. 调用 `manager` 的配置/运营接口
3. 配置优惠券、运营规则、管理参数
4. 相关配置影响订单、设备或用户侧业务

### 7.3 设备通信链路（典型）

可能的业务流程：

1. 设备与 `communicate` 建立 TCP/Netty 连接
2. 上报心跳、重量、事件等设备消息
3. `communicate` 解析协议并转给 `device`
4. `device` 处理业务逻辑并更新状态
5. 若订单侧需要开门，由 `order` / `device` 触发设备动作

## 8. 对“是否是一个管理端 + 一个 App 端”的判断

### 结论
这个判断**方向是对的，但不完整**。

更准确的说法应该是：

## `smart-container` = 管理端 + 用户移动端 + 设备通信端

其中：
- **管理端**：主要是 `manager`
- **用户移动端**：主要是 `order + channel + account(部分)`
- **设备通信端**：主要是 `communicate + device`

所以如果只说“一个管理端一个 app 端”，会遗漏最关键的一层：

### **设备侧通信与控制体系**

而这恰恰是这个项目区别于普通电商/后台系统的核心特征。
