# smart-container 数据库表与业务对象对应说明

> 更新时间：2026-05-30

## 1. 文档目的

本文档用于梳理 `smart-container` 项目中核心业务对象、Java 实体类、Mapper XML 中对应的数据表，以及这些对象在业务链路中的角色，帮助从“数据模型”视角理解系统。

本文档重点关注以下对象：

- 用户（Customer）
- 订单（Order）
- 设备（Device）
- 仓门（Gate）
- 优惠券配置（CouponConfig）
- 签约关系（CustomerAgreementSign）
- 验证码（VerifyCode）
- 秒杀对象（FlashSale）

> 说明：本文档根据实体类、Mapper XML、业务命名与现有代码整理，不等同于完整数据库设计说明。当前仓库中未提供完整建表 SQL，因此部分内容基于 Mapper 与实体字段推断。

## 1.1 2026-05-31 管理端补充表与 Mapper 归属

管理端新增页面补齐后，后台接口已统一改为 MyBatis Mapper XML 访问数据库，不再在新增管理端 Controller 中直接写 SQL。

新增或补齐的管理端业务表：

- `order_item`：订单商品明细
- `order_refund_record`：订单退款记录
- `order_adjust_record`：订单补扣/调整记录
- `order_exception_record`：订单异常处理记录
- `coupon_issue_record`：优惠券发放/领取记录
- `coupon_use_record`：优惠券使用记录
- `operation_log`：统一管理端操作日志/审计日志
- `payment_operation_record`：退款、补扣等支付操作幂等流水

新增 Mapper XML 归属：

- `OrderManageMapper.xml`：订单列表、详情、商品明细、退款、补扣、异常处理
- `CustomerManageMapper.xml`：用户列表、详情、签约记录、订单历史、状态维护
- `DeviceManageMapper.xml`：设备列表、仓门维护、设备事件处理、远程命令事件记录
- `AuthManageMapper.xml`：管理员登录、角色权限、接口权限校验
- `CouponFlowManageMapper.xml`：优惠券发放、撤回、领取/使用流水
- `AuditLogManageMapper.xml`：操作日志查询和统计
- `ManagerLogMapper.xml`：管理端统一审计日志落库
- `PaymentOperationMapper.xml`：支付操作幂等流水

支付流水语义：

- `payment_operation_record.request_no` 是退款/补扣幂等键。
- `channel_type = LOCAL_SIMULATED` 表示本地模拟通道，状态可为 `SUCCESS`。
- `channel_type = ALIPAY` 或 `WECHAT` 在未配置真实商户参数前只会记录 `PENDING_CONFIG`，用于防止误判真实资金已处理。
- 2026-05-31：`payment_operation_record` 增加 `error_code`、`channel_request_payload`、`channel_response_payload`，用于记录真实支付通道请求响应和错误码，字段内不得存放密钥或证书。
- 2026-05-31：微信退款会把 `order_info.pay_amount` 作为原订单总金额传给微信，退款金额仍来自管理端请求金额；支付宝和微信真实通道均使用 `request_no` 作为退款幂等号。
- 2026-05-31：`channel_message` 调整为 `TEXT`，并在代码层截断返回给前端的消息，避免第三方网关返回 HTML 错误页时导致审计流水落库失败。

账号权限初始化：

- `work/管理端账号权限初始化_20260531.sql` 用于初始化 `admin`、`operator`、`device_admin` 三类本地/线上管理账号。
- 脚本会补齐 `sys_admin_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission` 五类权限相关表及数据。
- 脚本使用 `CREATE TABLE IF NOT EXISTS`、`INSERT ... ON DUPLICATE KEY UPDATE`、`INSERT IGNORE`，支持重复执行。
- 当前本地验证结果：`admin` 具备全部 ACTIVE 权限，`operator` 具备运营、用户、订单、优惠券权限，`device_admin` 具备设备相关权限。

## 2. 总体理解

从当前代码结构看，系统核心数据域大致可以分为四组：

### 2.1 用户域
负责记录消费者身份、手机号、第三方平台标识。

核心对象：
- `CustomerEntity`
- `CustomerAgreementSignEntity`
- `VerifyCodeEntity`

### 2.2 订单域
负责描述用户在货柜中的一次购物行为。

核心对象：
- `OrderInfoEntity`
- `FlashSaleEntity`

### 2.3 设备域
负责描述货柜、仓门、设备状态和设备动作。

核心对象：
- `DeviceInfoEntity`
- `GateInfoEntity`

### 2.4 运营配置域
负责描述后台配置的活动、优惠券等策略。

核心对象：
- `CouponConfigEntity`

## 10. 当前仓库中可见的数据建模特点

### 10.1 领域划分比较清楚
- 用户域
- 订单域
- 设备域
- 配置域

### 10.2 关系主要通过业务 ID 串联
比如：
- `customerId`
- `orderNo`
- `deviceId`
- `gateId`

这说明系统在设计上更多依赖“业务主键串联”，而不是只依赖数据库自增 ID。

### 10.3 部分 Mapper 质量不一致
从现有代码可见：
- 有些 Mapper 比较规范
- 有些表名/字段名/insert 语句存在不严谨甚至错误的情况

这也解释了为什么本地联调过程中会出现多处 MyBatis 启动问题。

## 11. 结论

从数据库与业务对象视角看，这个项目的核心主线非常明确：

- `CustomerEntity` 负责用户主数据
- `OrderInfoEntity` 负责订单主数据
- `DeviceInfoEntity` / `GateInfoEntity` 负责设备主数据
- `CustomerAgreementSignEntity` 负责支付签约数据
- `VerifyCodeEntity` 负责验证码与校验数据
- `CouponConfigEntity` 负责运营配置数据

这套对象共同支撑了一个典型的智能货柜系统：

## **用户 → 订单 → 设备 → 支付/签约 → 运营配置影响业务结果**

如果继续往下深入理解系统，最有价值的下一步会是：

1. 把 DTO / BO / Entity 的映射关系再整理一版
2. 把每条业务链路中的“表变化顺序”串起来
3. 如果能接数据库，再补一份真实表结构核对文档
