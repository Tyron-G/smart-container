# smart-container 数据库表与业务对象对应说明

> 更新时间：2026-05-30

## 1. 文档目的

本文档用于梳理 `smart-container` 项目中核心业务对象、Java 实体类、Mapper XML 中对应的数据表，以及这些对象在业务链路中的角色，帮助从“数据模型”视角理解系统。

本文档重点关注以下对象：

- 用户（Customer）
- 订单（Order）
- 设备（Device）
- 仓门（Gate）
- 优惠券配置（CouponConfig）
- 签约关系（CustomerAgreementSign）
- 验证码（VerifyCode）
- 秒杀对象（FlashSale）

> 说明：本文档根据实体类、Mapper XML、业务命名与现有代码整理，不等同于完整数据库设计说明。当前仓库中未提供完整建表 SQL，因此部分内容基于 Mapper 与实体字段推断。

---

## 2. 总体理解

从当前代码结构看，系统核心数据域大致可以分为四组：

### 2.1 用户域
负责记录消费者身份、手机号、第三方平台标识。

核心对象：
- `CustomerEntity`
- `CustomerAgreementSignEntity`
- `VerifyCodeEntity`

### 2.2 订单域
负责描述用户在货柜中的一次购物行为。

核心对象：
- `OrderInfoEntity`
- `FlashSaleEntity`

### 2.3 设备域
负责描述货柜、仓门、设备状态和设备动作。

核心对象：
- `DeviceInfoEntity`
- `GateInfoEntity`

### 2.4 运营配置域
负责描述后台配置的活动、优惠券等策略。

核心对象：
- `CouponConfigEntity`

---

## 3. 业务对象与表对应关系总览

| 业务对象 | 实体类 | 主要对应表 | 主要模块 | 说明 |
|---|---|---|---|---|
| 用户 | `CustomerEntity` | `customer` | order / channel | 消费者基础身份信息 |
| 订单 | `OrderInfoEntity` | `order_info` | order | 订单主表 |
| 设备 | `DeviceInfoEntity` | `device_info` | device | 货柜设备主表 |
| 仓门 | `GateInfoEntity` | `gate_info` | device | 设备中的门体信息 |
| 优惠券配置 | `CouponConfigEntity` | 推断为优惠券配置表 | manager | 后台运营配置对象 |
| 签约关系 | `CustomerAgreementSignEntity` | `customer_agreement_sign` | channel | 用户与支付宝签约信息 |
| 验证码 | `VerifyCodeEntity` | `verify_code` | order | 手机验证码记录 |
| 秒杀/抢购对象 | `FlashSaleEntity` | 未直接看到 Mapper | order | 秒杀相关业务对象 |

## 4. 用户域对象

## 4.1 CustomerEntity

### 实体类
- `container-common/container-common-core/src/main/java/cn/fuguang/entity/CustomerEntity.java`

### 主要字段
- `id`：主键
- `customerId`：客户业务 ID
- `userName`：姓名
- `wechatOpenId`：微信 openId
- `aliOpenId`：支付宝 openId
- `mobile`：手机号
- `status`：状态
- `createTime`
- `updateTime`
- `remarks`

### Mapper 对应
#### order 模块
- `container-order/src/main/resources/mapper/CustomerMapper.xml`

#### channel 模块
- `container-channel/src/main/resources/mapper/CustomerMapper.xml`

### 对应表
- `customer`

### 业务意义
该对象代表系统中的消费者基础身份信息，是用户端业务的核心主数据。

### 典型使用场景
- 绑定支付宝/微信身份
- 查询用户是否已存在
- 与订单建立关联
- 判断用户当前业务状态

### 关键关系
- 与 `OrderInfoEntity.customerId` 关联
- 与 `CustomerAgreementSignEntity.customerId` 关联
- 与 `VerifyCodeEntity.mobile` 有业务联动关系

## 10. 当前仓库中可见的数据建模特点

### 10.1 领域划分比较清楚
- 用户域
- 订单域
- 设备域
- 配置域

### 10.2 关系主要通过业务 ID 串联
比如：
- `customerId`
- `orderNo`
- `deviceId`
- `gateId`

这说明系统在设计上更多依赖“业务主键串联”，而不是只依赖数据库自增 ID。

### 10.3 部分 Mapper 质量不一致
从现有代码可见：
- 有些 Mapper 比较规范
- 有些表名/字段名/insert 语句存在不严谨甚至错误的情况

这也解释了为什么本地联调过程中会出现多处 MyBatis 启动问题。

## 11. 结论

从数据库与业务对象视角看，这个项目的核心主线非常明确：

- `CustomerEntity` 负责用户主数据
- `OrderInfoEntity` 负责订单主数据
- `DeviceInfoEntity` / `GateInfoEntity` 负责设备主数据
- `CustomerAgreementSignEntity` 负责支付签约数据
- `VerifyCodeEntity` 负责验证码与校验数据
- `CouponConfigEntity` 负责运营配置数据

这套对象共同支撑了一个典型的智能货柜系统：

## **用户 → 订单 → 设备 → 支付/签约 → 运营配置影响业务结果**

如果继续往下深入理解系统，最有价值的下一步会是：

1. 把 DTO / BO / Entity 的映射关系再整理一版
2. 把每条业务链路中的“表变化顺序”串起来
3. 如果能接数据库，再补一份真实表结构核对文档
